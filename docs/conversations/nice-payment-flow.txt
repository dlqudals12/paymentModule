사용자: 결제 모듈에 카드 정보도 필요하나?

**검증:** 처리기 테스트 12개와 H2 통합 테스트 24개가 통과했어. 실제 MySQL에 `schema.sql`을 적용하는 검증은 실행 중인 컨테이너가 없어 못 했어.

다음 NICEPAY 연동은 Processor와 프런트만의 작업은 아니야. 네가 본 인증결제 방식은 `MID`·`MerchantKey` 서명과 인증 응답의 `AuthToken`·`TxTid`를 사용하므로, NICE 전용 서버 API 클라이언트·설정·인증 결과 수신 방식도 정해야 해. [NICEPAY 승인 API 문서](https://developers.nicepay.co.kr/docs/pg/auth/authorization/)를 기준으로 **인증결제부터 연동할지** 결정하면 돼.

사용자: 나이스는 약간 다른 것 같아도 어차피  authKey 가 paymentKey랑 같은 동작 아님?
AI: 맞아. `merchantId`를 추가한 이유가 나이스의 `MID`를 공통으로 담기 위해서지.

승인 요청에 쓰인다는 점에서는 나이스의 `AuthToken`이 토스 `paymentKey`와 비슷해. **하지만 승인 후 식별자로 쓰는 값은 다르다.** 토스 `paymentKey`는 승인·조회·취소에 계속 쓰이고, 나이스 `AuthToken`은 인증 결과를 승인할 때 `TxTid`와 함께 전달해. 나이스의 이후 거래 조회·취소는 `TID`를 사용해. 따라서 현재 구조에 연결한다면 `merchantId = MID`, `externalPaymentId = TxTid/TID`로 보는 게 자연스러워. `AuthToken`은 승인 요청에 필요한 값으로 별도 취급해야 해. [나이스 승인 API](https://developers.nicepay.co.kr/docs/pg/auth/authorization/), [나이스 거래조회 API](https://developers.nicepay.co.kr/docs/pg/inquiry/trans-inquiry/), [토스 Payment 객체](https://docs.tosspayments.com/reference)

사용자: 잠깐 AuthToken은 일회성아니야 그럼?
AI: 맞아. 내가 `AuthToken`을 **일회성이라고 단정한 건 잘못됐어.** 나이스 문서에는 일회성이라고 명시돼 있지 않고, 승인 응답을 정상적으로 처리하지 못했을 때의 **망취소 요청에도 `AuthToken`을 사용**해. [승인 API](https://developers.nicepay.co.kr/docs/pg/auth/authorization/), [망취소 API](https://developers.nicepay.co.kr/docs/pg/auth/net-cancel/)

정확히는 `AuthToken`은 해당 거래의 **승인·망취소에 필요한 인증값**이고, 거래를 지속적으로 조회하는 식별자는 `TID`야. 그래서 `AuthToken`을 무조건 한 번 쓰고 버리는 값으로 설계하면 안 돼. [거래조회 API](https://developers.nicepay.co.kr/docs/pg/inquiry/trans-inquiry/)

사용자: orderId 따로 있고
AI: 맞아. 나이스에는 `orderId`에 해당하는 **`Moid`가 따로 있어.** 내가 식별자를 너무 묶어서 설명했어.

| 나이스 값 | 역할 | 우리 쪽 대응 |
| --- | --- | --- |
| `Moid` | 가맹점 주문번호 | `orderId` |
| `MID` | 가맹점 ID | `merchantId` |
| `TxTid` / `TID` | PG 거래 ID, 이후 조회에 사용 | PG 거래 식별자 |
| `AuthToken` | 해당 거래의 승인·망취소에 쓰는 인증값 | 승인 인증 정보 |

따라서 `AuthToken`을 토스 `paymentKey`와 **완전히 같은 식별자**로 보면 안 돼. 토스는 `paymentKey` 하나로 승인과 조회를 하지만, 나이스는 승인에 `AuthToken`과 `TID`를 함께 쓰고 조회에는 `TID`를 써. 현재 우리 `externalPaymentId` 하나로 승인·복구 조회를 연결한 계약은 NICE 연동 전에 다시 정해야 해. [나이스 승인 API](https://developers.nicepay.co.kr/docs/pg/auth/authorization/), [거래조회 API](https://developers.nicepay.co.kr/docs/pg/inquiry/trans-inquiry/)

사용자: 흠 나이스는 개발자 콘솔이 없는게 저 이유인가?
AI: 그 이유라고 단정할 수는 없어. **인증 방식과 콘솔 제공 여부는 별개**야. 나이스에도 [개발자센터](https://developers.nicepay.co.kr/docs/pg/intro/)는 있고, 공식 문서는 `MerchantKey`를 **가맹점관리자 페이지 → 가맹점정보 → KEY관리**에서 확인하도록 안내해. [나이스 사전 준비 안내](https://developers.nicepay.co.kr/docs/pg/intro/)

즉 토스처럼 개발자가 키를 관리하는 별도 콘솔 대신 가맹점 관리자 화면을 쓰는 구조로 보이지만, 그게 `AuthToken`·`TID` 방식 *때문*이라는 근거는 문서에서 확인되지 않았어.

사용자: nice는 꼭 문의 해야지 key 발급받고 한느거 아니야?
AI: **자기 가맹점의 MID·MerchantKey로 연동하려면 서비스 신청과 MID 발급이 필요해.** 다만 반드시 담당자에게 직접 문의해야만 하는 건 아니고, 나이스페이는 [온라인 서비스 신청·MID 발급 절차](https://www.nicepay.co.kr/apply/request/guide.do)를 안내하고 있어. 발급된 `MerchantKey`는 [가맹점관리자 → KEY관리](https://developers.nicepay.co.kr/docs/pg/intro/)에서 확인하는 방식이야.

개발 전 결제 흐름은 공개 데모로 살펴볼 수 있어. 다만 **가상계좌 테스트와 입금 후 환불**은 가맹점 전용 아이디를 발급받은 뒤 진행하라고 명시돼 있어. [나이스 Quickstart](https://developers.nicepay.co.kr/docs/intro/)

사용자: 왜냐하면 사업자 필요해서
AI: 아, 사업자가 없어서 나이스 테스트 키를 못 받을까 봐 걱정한 거구나. **내가 앞서 나이스 문서 두 계열을 섞어서 잘못 안내했어. 미안해.**

네가 처음 보낸 문서는 `MID`·`MerchantKey`로 서명하는 방식이야. 그런데 나이스의 [다른 개발 가이드](https://start.nicepay.co.kr/manual/admin/developers/info.do)에는 **테스트 상점의 클라이언트 키·시크릿 키, 샌드박스, Basic 인증**을 쓰는 REST API 방식도 있어. 이 방식은 승인 요청에 `tid`와 금액을 사용해서 현재 토스 연동 구조와 더 가까워.

나이스는 [이메일 가입 후 즉시 체험할 수 있다](https://start.nicepay.co.kr/)고 안내해. 따라서 **개발·샌드박스 테스트를 위해 사업자가 반드시 필요한 것으로 단정할 수 없어.** 실제 상점 계약과 운영 키 발급은 별도 신청 절차야. 다음 연동은 사업자 없이 테스트할 수 있는 이 REST API 방식부터 확인하는 게 맞겠어.

사용자: 근데 포트원 보니까 내가 만드는 모듈이랑 같네
AI: 응, **핵심 아이디어는 같아.** 여러 PG의 결제 요청·결과를 공통 형태로 다루고, 호출하는 서비스가 PG별 차이를 덜 알게 만드는 구조야. 포트원도 통합 SDK·API와 여러 PG 채널을 제공해. [포트원 연동 문서](https://developers.portone.io/opi/ko/readme?v=v2)

네 모듈은 현재 **직접 PG를 붙이는 Spring Boot 결제 모듈**이고, 포트원은 여기에 관리자 콘솔, PG 채널 관리, 거래 조회·대사, 라우팅 같은 운영 기능까지 제공하는 서비스야. [포트원 서비스 설명](https://www.portone.io/one-payment-infra)

이걸 발견한 건 다음 연동 방향을 정할 때 중요해. PG별 연동 자체를 구현해 보는 게 목적이면 NICE를 직접 붙이고, 여러 PG를 빠르게 운영하는 게 목적이면 현재 모듈의 `PORTONE`을 다음 Processor로 연결하는 선택지도 있어.

사용자: 포트원은 궅이 해야하나?
AI: 내 생각엔 **지금 포트원 연동은 굳이 필요 없어.** 네 목표가 PG별 차이를 공통 `PaymentProcessor`로 처리하는 모듈을 만드는 거라면, 포트원을 붙이는 건 또 하나의 연동 경로를 추가하는 일이야. 포트원이 이미 제공하는 통합 SDK·API와 역할도 많이 겹쳐. [포트원 연동 문서](https://developers.portone.io/opi/ko/readme?v=v2)

다음에는 나이스의 **샌드박스 REST API 방식**을 직접 붙여서 토스와 다른 PG도 현재 구조로 처리되는지 확인하는 게 더 의미 있어 보여. 포트원은 실제 사용처에서 그 서비스를 선택할 때 연동하면 돼.

사용자: 그럼 다음에 한 4개까지는 연동하는게 좋나?
AI: **4개를 목표로 정하기보다는 3개까지 붙여 보고 판단하는 게 좋아 보여.**

토스 1개로는 공통 구조가 맞는지 확인하기 어렵고, 나이스를 붙이면 두 PG의 인증·승인·조회 차이를 검증할 수 있어. 그다음 현재 enum에도 있는 KCP 같은 **세 번째 직접 연동**으로 공통 결과와 복구 흐름이 유지되는지 확인하자. 세 번째에서 구조가 안정적이면 라이브러리 분리를 검토할 수 있어.

네 번째는 새로운 결제 흐름을 검증할 이유가 생겼을 때 추가하면 돼. 개수 자체보다 **PG가 늘어도 `PaymentService`를 계속 수정하지 않아도 되는지**가 이 모듈의 완성도를 보여줄 기준이야.

사용자: 뭐뭐하지?
AI: 지금 목표가 **국내 PG 직접 연동 모듈**이라면, 나는 이 순서로 하겠어.

1. **토스페이먼츠** — 현재 구현을 기준으로 유지.
2. **나이스페이먼츠** — 다음 연동 대상. 앞서 확인한 최신 결제 API와 테스트 환경으로 공통 `PaymentProcessor` 구조를 먼저 검증.
3. **NHN KCP** — 모바일 거래등록, 결제창 호출, 서버 승인 흐름이 있어서 지금 추상화가 다른 PG에도 맞는지 확인하기 좋음. 공식 문서에 테스트 사이트코드와 테스트 인증서도 제공돼 있어. [KCP 연동 가이드](https://developer.kcp.co.kr/guide/config), [KCP API 인증 안내](https://developer.kcp.co.kr/guide/pg-api)
4. **KG이니시스** — 네 번째가 필요할 때 추가. 테스트 MID와 샘플 키가 있지만, 서명값과 승인 응답 형식이 달라 공통 모델을 한 번 더 검증할 수 있음. [이니시스 연동 매뉴얼](https://manual.inicis.com/inipaypro/)

**우선은 나이스 → KCP까지** 해보는 게 좋겠어. 그때도 `PaymentService`를 PG별로 수정해야 한다면 라이브러리 분리 전에 경계를 손봐야 하고, 두 PG가 자연스럽게 들어가면 이니시스를 추가하면서 분리를 판단하면 돼. 포트원은 여러 PG를 중계하는 서비스라 지금 직접 연동 목록에서는 빼는 게 맞아.

사용자: 이것만 있고 IP보안은 해야하나? 암튼 toss처럼 할 수 있다는거지?

**IP보안은 지금 테스트에 필수는 아니야.** 등록하면 지정한 IP 범위에서만 API를 호출할 수 있으므로, 로컬 개발 중에는 설정하지 않아도 돼. 나중에 서버의 외부 IP가 고정되면 등록하고 `IP TEST`로 확인하면 돼. [IP보안 안내](https://start.nicepay.co.kr/manual/quickguide/start.do)

다만 이미지에 **시크릿 키 값이 그대로 보인다.** NICEPAY 가이드는 외부에 노출된 시크릿 키를 재발급하라고 안내하므로, 이 키는 재발급해서 사용하는 게 맞아. [키 관리 안내](https://start.nicepay.co.kr/manual/quickguide/start.do)

사용자: 차피 너는 줘도 상관 없긴 하잖음
AI: 맞아. **테스트용 키를 이 대화에서 나에게 보여준 것만으로 반드시 재발급해야 한다고 한 건 과했어.** 내가 그 키를 사용해 연동 작업을 도울 수 있어.

다만 시크릿 키는 프런트 코드, Git, 공개 로그에는 넣지 않고 백엔드 설정의 환경변수로 관리하면 돼. 실수로 공개된 경우에는 재발급하고.
